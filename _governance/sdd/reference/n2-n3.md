# Référence SDD — niveaux N2 et N3

> À placer dans `_governance/sdd/reference/n2-n3.md`. Document à transformer en templates, skills et règles de check_gates **à la première activation** du niveau concerné. Il n'est jamais chargé en session courante.

---

## N2 — Contrats

### Artefacts ajoutés

```
{projet}/specs/
  02-architecture.md     ← inclut le glossaire (section dédiée)
  contracts/             ← code : types, schémas ; seul propriétaire = l'architecture
  adr/                   ← un ADR par choix structurant
  changes/               ← CR-NNN.md
  escalations/           ← ESC-NNN.md
  qc/                    ← rapports QC-ARCHI
```

La **traçabilité** n'est pas une matrice tenue à la main. Elle est générée par script à partir du frontmatter des specs, des tests et des modules (`exigences: [EF-03]`, `jalon: J2`).

### Squelette ambulant

Le jalon 0 de N2 est un parcours de bout en bout qui traverse tous les modules avec des implémentations minimales. Les specs de modules (N3) sont rédigées juste-à-temps, quand le jalon actif en a besoin.

### Gates N2

| Gate | Condition | Qui valide |
|---|---|---|
| G0 — Architecture | QC-ARCHI sans bloquant | relecteur + moi |
| G1 — Contrats | contrats compilent ; tests de contrat ; jalon 0 démontré | relecteur |

### QC-ARCHI

Critères **B** (bloquant), **M** (majeur), **m** (mineur). Chaque rapport cite l'extrait fautif et propose une correction. Le résultat est présenté sous forme des 5 défauts les plus structurants, formulés en questions.

- **Rattachement**
  - (B) Chaque exigence est rattachée à un jalon et à la mission.
  - (B) Aucun module ne sert aucun jalon.
- **Exigences**
  - (B) Exigences fonctionnelles numérotées (EF-NN), chacune avec un critère d'acceptation vérifiable.
  - (M) Exigences non fonctionnelles chiffrées.
  - (B) Aucun verbe flou sans critère.
- **Domaine**
  - (B) Glossaire.
  - (B) Modèle des entités partagées.
  - (M) Invariants métier énoncés.
- **Décomposition**
  - (B) Chaque module a une responsabilité unique.
  - (B) Graphe de dépendances déclaré et acyclique.
  - (M) Chaque module tient dans une session.
- **Contrats**
  - (B) Chaque arête du graphe a un contrat.
  - (B) Chaque donnée persistée a un seul propriétaire en écriture.
  - (M) Sémantique des échanges précisée.
- **Transverse**
  - (M) Stratégies définies : erreurs, logs, secrets, authentification, persistance, tests, déploiement.
- **Incertitudes**
  - (M) Un ADR par choix structurant.
  - (B) Chaque incertitude est associée à un spike.
- **Clarté**
  - (B) Aucun TBD dans un élément bloquant.
  - (M) Aucun qualificatif non quantifié.
- **Test de dérivation** (facultatif, si le projet a plus de 5 modules) : un relecteur qui n'a jamais vu le projet retrouve les modules et le graphe à partir de la seule spec.

### Gestion du changement

On ne modifie jamais une spec en silence pendant une implémentation. Le coût d'un changement est proportionné à son niveau.

| Niveau | Exemple | Qui décide | Traitement | Propagation |
|---|---|---|---|---|
| 0 — Local | choix interne au module | exécutant | une ligne dans le rapport de lot | aucune |
| 1 — Spec module | cas limite ajouté | architecte | spec et tests mis à jour, QC en delta | ce module revient à G2 |
| 2 — Contrat / architecture | champ ajouté, frontière déplacée | architecte, moi informé | CR + ADR + analyse d'impact | consommateurs revus ; recentrage |
| 3 — Mission / principes / jalons | nouveau besoin | moi uniquement | CR + revue de la roadmap | jurisprudence réexaminée ; recentrage |

**CR** : niveau, origine, justification rattachée à la mission, impact calculé depuis la traçabilité, plan de migration.

**Éviter les cascades** : changements additifs (ajouter, migrer les consommateurs, retirer l'ancien) ; contrats versionnés ; un module en cours est mené à un point stable avant d'être modifié.

**Dérive spec / code** : à chaque jalon, le relecteur compare specs et code réel. Tout écart est corrigé par une CR, dans un sens ou dans l'autre.

### Ajouts à check_gates en N2
- Graphe d'imports conforme au graphe déclaré.
- Aucun type partagé redéfini hors `contracts/`.
- Escalades et CR ouvertes signalées.
- Traçabilité générée sans trou bloquant.

### Adoption sur un projet existant
Rédiger une spec **telle que construite**, puis extraire les contrats des interfaces réelles. Si le socle structurel a été respecté depuis N1, les types sont déjà dans `contracts/`.

## N3 — Délégation contrôlée

### Artefacts ajoutés

```
{projet}/specs/
  sdd.yaml               ← rigueur par module (complète | allégée)
  modules/{module}.md
  qc/                    ← rapports QC-MODULE
{projet}/tests/acceptance/
```

`STATUS.md` est **généré** par script (gate atteinte par module, rigueur, statut « hérité »), jamais tenu à la main.

### Rigueur par module
- **Complète** : logique métier, données partagées, sécurité.
- **Allégée** : modules périphériques. Seuls les critères marqués *(allégé)* s'appliquent, et G4 est fusionné dans G3 par contrôle automatique.

### Gates N3

| Gate | Condition | Qui valide |
|---|---|---|
| G2 — Spec module | QC-MODULE ; simulation d'exécutant ; tests d'acceptation rouges ; empreinte des tests et contrats enregistrée | relecteur |
| G3 — Implémenté | tests verts ; aucune escalade ouverte ; empreintes inchangées | exécutant |
| G4 — Conforme | revue de conformité (imports, contrats, périmètre) | relecteur ≠ exécutant |

### QC-MODULE
- (B) Jalon servi et exigences couvertes cités ; hors-périmètre explicite. *(allégé)*
- (B) Interfaces qui référencent `contracts/` sans redéfinir de type. *(allégé)*
- (B) Dépendances consommées exactement conformes au graphe. *(allégé)*
- (B) Cas nominaux, limites et erreurs décrits.
- (B) État, persistance et effets de bord explicites.
- (B) Tests d'acceptation qui couvrent chaque exigence et chaque erreur de contrat, et sont rouges. *(allégé)*
- (B) Décisions laissées à l'exécutant listées, toutes locales.
- (M) Principes pertinents pour les choix locaux rappelés.
- (M) Taille et budgets non fonctionnels définis.
- **Simulation d'exécutant** (toujours) : un relecteur reçoit le briefing et liste les questions qu'il devrait poser. Toute question portant sur une décision non locale est bloquante.
- **Tests de mutation** (rigueur complète uniquement, sur échantillon) : mutations simples sur un squelette ou une implémentation de référence ; des tests qui ne les détectent pas sont un défaut majeur.

### Rôles en N3

| Rôle | Responsabilité | Affectation par défaut |
|---|---|---|
| orchestrateur / arbitre | CAP, découpage, arbitrages, jurisprudence | celui du frontmatter |
| rédacteur de specs | architecture, specs, contrats, tests | l'orchestrateur |
| relecteur | QC, tests d'arbitrage, de dérivation, de simulation, conformité | un fournisseur différent de l'auteur si autorisé ; sinon session neuve forkée |
| exécutant | code d'un module à partir du briefing | parmi `executants_autorises` |
| git | commits, merges | exécutant git dédié |

Le briefing de N3 étend celui de N1 avec la spec du module et les tests d'acceptation. Le parallélisme se fait par worktrees, fusionnés par l'exécutant git.

### Ajouts à check_gates en N3
- Cohérence de STATUS.md généré.
- Présence des rapports QC exigés par la gate.
- État des tests conforme à la gate.
- Comparaison des empreintes de tests et contrats entre G2 et G3.

### Adoption sur un projet existant — effet cliquet
Les gates ne s'appliquent qu'aux modules créés ou modifiés après l'activation. Les autres sont marqués « hérité » dans STATUS.md.
